# Research

This document records research that may influence engineering practices,
project standards, workflows, or architectural decisions.

Research is not automatically treated as a permanent rule.

Ideas should be evaluated, tested when practical, and promoted only when
there is sufficient evidence that they are useful.

---

**Category:**

AI Engineering / Documentation / Other

**Source:**
Where did the idea come from?

**Author / Organization:**
Optional. Include only when relevant.

**Main Idea:**

**General Interpretation:**

**Candidate Practice:**

**Experiment Idea:**

**Evidence:**

**Related Lesson:**
Relevant `LESSONS.md` entry, if any.

**Related Decision:**
Relevant `DECISIONS.md` entry, if any.

# Research Categories

Research may include topics such as:

- software engineering practices,
- code quality,
- testing strategies,
- review workflows,
- automation,
- repository management,
- agent coordination,
- AI-assisted development,
- documentation,
- architecture,
- security,
- maintainability,
- developer experience.

The template should not depend on any specific tool, model, vendor,
programming language, or project type.

---

# Source Evaluation

Research sources should be evaluated critically.

Consider:

- Is the source reliable?
- Is the idea supported by evidence?
- Is the idea broadly applicable or context-specific?
- Does it conflict with existing project standards?
- Can it be tested?
- What trade-offs does it introduce?

A respected author or popular tool is not sufficient evidence by itself.

---

# From Research to Template

Useful ideas should not remain only as research notes.

When an idea is supported by sufficient evidence, it may influence:

- project instructions,
- agent responsibilities,
- testing requirements,
- review rules,
- workflow design,
- documentation practices,
- or engineering standards.

This allows external ideas to improve the template without making the
template dependent on their original source.

# Research Rules

1. Do not treat an idea as true only because a respected person or
   organization proposed it.

2. Prefer original or reliable sources when possible.

3. Separate the source's original idea from the project's interpretation.

4. Do not attribute a rule to a source without sufficient evidence.

5. Store uncertain ideas as research rather than permanent standards.

6. Test candidate practices when practical.

7. Record unsuccessful evaluations as well as successful ones.

8. Promote practices based on usefulness and evidence, not popularity.

9. Prefer reusable engineering principles over tool-specific instructions.

10. Keep the base template general. Add project-specific research only
    after the template has been adopted for a concrete project.
